## 现场证据

旧实现使用阻塞式事务锁。此前完整云端回归在管理身份/5432 下为 76 项中 71 项通过，在实际 `ccagent_runtime`/6543 下为 76 项中 69 项通过。失败涉及并发充值、退款、授权及后续依赖检查；原始日志保留。

随后以同一受限运行身份、8 个客户端连接、相同的重复入账/混合读取/并发授权场景，对 `postgres 4.1.0` 和临时安装的 `pg 8.23.1` 做对照。两款驱动均出现超时，未替换正式驱动。记录位于 `output/checks/wallet-driver-*-trial-*.log`；后续试验可能受到前轮未结束的服务端查询影响，不能把六轮结果当作互相独立的稳定性样本。

独立原生客户端记录了服务端活动及锁：部分会话的事务锁已显示获授予，其等待状态仍为 `Lock/advisory`，没有可见阻塞者，并阻塞同键的其他会话。观测持续多次采样，记录在 `wallet-driver-database-observer.log`。记录仅包含随机测试 Schema、进程/等待事件、语句摘要与锁元数据，没有查询正文、参数、数据库地址、用户名、密码或用户对话。该现象用于选择应用层可验证的处理方式，尚不足以断定 PostgreSQL、连接池或平台内部的具体根因。

Windows PowerShell 重定向的 `.log` 可能带 UTF-16LE BOM，程序读取时需按 BOM 选择编码；直接用 UTF-8 正则扫描可能误判为没有事件。驱动自有的 `database-trace-*.jsonl` 由脚本直接以 UTF-8 写入。六个对照 Schema 已另行核对，均已删除且没有活跃查询；诊断观察器与试验进程已结束。

## 当前实现

`0003_wallet_account_lock.sql` 增加私有的 `acquire_mutex(bigint)` 和 `lock_wallet(text)`。它们使用 [PostgreSQL 的非阻塞事务锁](https://www.postgresql.org/docs/17/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS)：尝试未成功时短暂休眠，等待预算 5 秒且最多 250 次尝试，仍无法获锁则抛出 `55P03 / DATABASE_LOCK_BUSY`。事务提交或回滚释放锁。循环仅尝试获取锁，受保护的写入执行一次。

- 入账、调用授权、结算及释放，在访问账户的受保护数据前使用同一个账户事务锁。嵌套资金函数可重复取得本事务已持有的锁，不同账户使用不同锁。
- 查单入账、退款准备和退款结果处理，统一先取得账户锁，再锁订单及退款记录。需要再次核对锁定后的订单/退款归属，归属变化时拒绝写入。外部支付查单和退款 HTTP 请求继续在资金事务之外执行。
- 后台设置、角色变更和价格目录沿用原固定锁标识，统一通过有界获锁函数处理。原有版本冲突、充值范围、最后管理员和价格绑定约束保留。
- 已知忙碌状态转为 HTTP 503，提示“当前操作较多，请稍后重试。”；调用授权在此状态下不创建调用记录、不冻结金额，退款准备不建立退款单或联系支付方。连接关闭、客户端超时和未知支付结果继续按各自的待核对流程处理。
- 两个辅助函数采用调用者身份，`PUBLIC` 无执行权限；仅应用内部运行角色及所有者可调用。客户端不获得数据库凭据。运行角色仍不能直接写钱包或修改资金流水，原有三个资金函数的权限和金额校验保留。

配置和 SQL 需随迁移与应用版本一起发布，禁止只上线新调用代码而漏掉迁移。正式驱动、客户端查询/排队超时及原并发数量均未为了取得通过结果而放宽。
