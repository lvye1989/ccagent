# CCAGENT 应用检测与优化记录（2026-09-21）

## 范围与结论

本次在 Windows、Node.js 24.16.0、`ccdagent@0.1.2` 的 `jev` 开发分支检测代码、配置边界、依赖及发布包。优先修复了本地项目配置绕过信任边界的问题，并更新兼容的依赖。

发布检查通过不等于所有测试通过，也不是全面渗透测试或所有软件的实际操作验收。本轮没有重新执行真实 Rhino 建模、Google 授权或付费模型请求；相关回归使用隔离目录、假密钥、模拟模型与本地 MCP 服务。macOS 原生沙箱和 POSIX 安装器在本机跳过。

## 已完成：配置和密钥信任隔离

修复前，隔离测试使用假密钥证明四种情况均可发生：未信任项目重定向用户模型地址、通过新 Profile 引用用户环境密钥、提前应用项目 env、改写唯一 dotenv 路径。不需要发出真实网络请求即可证明请求构造所依赖的地址和密钥已被改写；没有证据表明本机曾发生真实泄漏。

修复内容：

- `src/services/api/providers/profile.ts` 仅从可信配置源加载模型 Profile；未信任项目不能覆盖地址、注入请求头或新增读取密钥的 Profile。
- `src/utils/loadEnv.ts` 先加载用户配置并固定唯一 `.env`，项目/local env 与隐式项目 `.env` 仅在信任后加载。
- 项目 env 不能通过该加载器更换用户目录/信任存储、唯一密钥文件、Node 加载器或 TLS 校验策略。
- 用户 settings 中相对 `.env` 路径以 settings 目录为基准，避免在不同项目中读到不同密钥文件。
- 再次加载配置会撤销上轮注入、但本轮不再可信的项目环境值；用户显式更改过的进程变量不会被无条件回滚。
- 交互式启动先询问信任，再加载项目配置和扩展；非交互启动不自动授予信任。
- 全部 `loadEnv` 调用点改为等待异步信任检查。Stage 30 测试使用独立用户目录并显式信任自己的测试项目。

用户显式信任的项目仍可配置自定义模型，因此应只信任可靠的仓库。用户选定的唯一 `.env` 在任意工作目录仍可使用，DeepSeek 不恢复为从 OS/settings 多路径寻找密钥。

新增命令：

```bash
npm run test:config-trust
npm run verify:repository
npm run verify:repository -- --staged
```

首项已加入 `verify:release`。仓库检查覆盖待提交路径、文本中的常见凭据格式及本地已知凭据匹配，只报告位置，不输出密钥。它是定向防护，不代替完整历史扫描或专业密钥扫描器。

同时忽略 `.env.*`（保留 `.env.example`），移除 4 个历史 Python 字节码文件的 Git 跟踪；本地文件保留，未删除用户建模成果。

## 已完成：兼容依赖更新

运行 `npm audit fix --ignore-scripts` 更新锁文件；高危 `fast-uri`、`hono`、`ip-address` 等问题已不再出现。复查为 0 高危、0 中危、1 低危。

剩余为 `tsup -> esbuild@0.27.7` 的 Windows 开发服务器文件读取问题，公告 [GHSA-g7r4-m6w7-qqqr](https://github.com/advisories/GHSA-g7r4-m6w7-qqqr)。当前 tsup 依赖范围为 `^0.27.0`，修复版超出该范围，普通 audit fix 无法消除。检查到本项目使用 esbuild 打包，未发现配置 esbuild 开发服务器的调用。没有为了让审计清零而强行跨版本覆盖；建议验证升级 tsup 或兼容的 esbuild override 后再处理。

`npm audit` 仍以退出码 1 报告这项低危，不能宣称“零漏洞”。依赖主要声明为 devDependencies，但部分库被打入 CLI，因此不能用 `--omit=dev` 掩盖风险。

## 后续优化建议

### 1. 优先修复配置写入的数据完整性

`src/utils/settings.ts` 的共享 `writeSettingsPatch` 直接读取、浅合并、写回，没有统一锁或原子替换，还忽略 JSON 解析错误。

在私有临时目录中的实际探针：32 个并发、不同键的更新只保留 1 个键；随后对损坏 JSON 写入一项配置，原内容被覆盖。没有触碰用户真实 settings。

建议采用按文件跨进程锁、锁内读取/更新、临时文件原子替换、损坏文件拒绝覆盖。`agentStates`、`mcpServerStates` 和权限数组也应迁移到锁内事务更新，不能只给最终 write 加锁而仍在锁外读取旧对象。补充多进程、嵌套字段竞争、崩溃恢复与损坏文件保留测试。在修复前避免多个 CCAGENT 实例同时更改配置。

### 2. 让测试基线与当前产品功能一致

`npm run test:queryengine` 的首处差异是 golden 21 个工具、当前 41 个工具；还有工具 token 估算及 Windows/macOS 沙箱状态差异。本轮没有直接 `--update` 掩盖差异。

建议固定 characterization 测试的工具集合和平台依赖，将新增能力放入独立断言，再经人工审阅更新基线。当前 `verify:release` 不包含该失败套件，所以发布检查绿灯不能理解为所有脚本都绿灯。

### 3. 加入普通提交/PR 的跨平台门禁

当前 `.github/workflows/release.yml` 仅由 `v*` tag 触发。建议普通 push/PR 即运行 Windows/Linux 的类型检查、安全回归、功能回归及构建；先阻止新增高/中危依赖，再逐步清理低危。真实 Rhino/Computer Use 验收应另设需人工触发、具备目标软件的 Windows 环境，避免在通用 CI 中伪装通过。

### 4. 检查真实终端的 TLS 环境

本次检测进程继承了 `NODE_TLS_REJECT_UNAUTHORIZED=0`，但 Windows User/Machine 环境记录均未设置，不能据此认定用户所有终端都关闭了校验。本次依赖下载/最终审计以局部 `=1` 执行成功，没有修改系统环境。建议确认实际启动终端；需要代理 CA 时安装可信 CA，不长期关闭 HTTPS 校验。
